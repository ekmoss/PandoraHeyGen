# Project Overview

## Project Description
Pandora is a customized version of the HeyGen Interactive Avatar demo, tailored specifically for Capgemini's trade show experience. The application provides an interactive AI avatar that can respond to voice or text input through a user-friendly interface optimized for touch screens in portrait mode.

## Key Features
- Full-screen portrait mode optimized for large touchscreen displays
- Push-to-talk interface with simple tap-to-toggle microphone control
- Auto-configuration with settings loaded from environment variables
- Capgemini branding with AUNZ colors and design language
- Admin panel accessible by typing "admin" and entering an access code
- Voice activity detection for efficient audio processing
- Performance optimization for low-latency responses
- Background removal and customization options
- RAG (Retrieval Augmented Generation) pipeline for knowledge-based responses

### Token API Routes
The application uses two distinct token routes for different services:

1. **/api/get-access-token**: 
   - Returns HeyGen API tokens required for the StreamingAvatar component
   - Uses the HEYGEN_API_KEY environment variable
   - Called during avatar initialization in InteractiveAvatar.tsx
   - Returns a plain text token (not JSON)
   - Uses POST method

2. **/api/speech-token**:
   - Returns Azure Speech Service tokens for speech-to-text functionality
   - Uses AZURE_SPEECH_KEY and AZURE_SPEECH_REGION environment variables
   - Returns a JSON object with token and region properties
   - Uses GET method

## OpenAI Service

### Overview
The `openai-service.ts` centralizes all OpenAI API interactions, providing a consistent interface for prompt formatting, API calls, response handling, and performance metrics tracking. It replaces direct API calls with a service layer that can be reused across components.

### Key Features
1. **Centralized Prompt Templates**: Maintains system prompts in one location for easy updates and standardization
2. **Consistent Message Formatting**: Standardizes how messages are formatted before being sent to OpenAI
3. **Unified Error Handling**: Implements consistent error handling and logging across all OpenAI interactions
4. **Performance Metrics**: Tracks detailed timing metrics for all operations in the OpenAI pipeline
5. **RAG Pipeline**: Implements a Retrieval Augmented Generation pipeline for knowledge-based responses

### Main Interfaces
- `ChatMessage`: Defines the structure for system/user/assistant messages
- `ChatOptions`: Configuration options for OpenAI calls including temperature, streaming, and RAG settings
- `ChatResponse`: Standard response structure with message content and metrics
- `RagDocument`: Structure for documents retrieved during the RAG process
- `RagCitation`: Structure for citations that can be returned with RAG responses

### Core Functions
- `formatChatMessages()`: Formats user messages with system prompts and context information
- `callChatApi()`: Makes the actual API call to OpenAI with proper error handling
- `processUserMessage()`: Main entry point for processing a user message (with or without RAG)
- `processWithRAG()`: Implements the complete RAG pipeline with document retrieval and context enhancement
- `parseJsonResponse()`: Helper for parsing non-streaming responses
- `prewarmConnection()`: Prewarms connections to the API to reduce latency

### RAG Pipeline
The Retrieval Augmented Generation pipeline provides document-based responses:

1. **Document Retrieval**: `retrieveRelevantDocuments()` finds relevant documents for a query
2. **Context Formatting**: `formatRetrievedDocuments()` formats retrieved documents as context
3. **Enhanced Prompting**: Combines user query with retrieved context and specialized RAG prompts
4. **Performance Tracking**: Measures timing for each stage of the RAG pipeline

### Usage
Components can use the OpenAI service like this:
```typescript
import { processUserMessage, parseJsonResponse } from 'services/openai-service';

// For standard chat
const response = await processUserMessage(userInput);
const result = await parseJsonResponse(response);

// For RAG-enhanced responses
const response = await processUserMessage(userInput, { useRAG: true });
const result = await parseJsonResponse(response);
```

## Lib vs Services Redundancies and Organization

### Current Organization Issues

1. **Functional Overlap:**
   - `app/lib/streamingAudio.ts` (499 lines) and `services/audio-recorder.ts` (140 lines) both handle audio recording and processing but with different approaches:
     - `streamingAudio.ts` uses utility functions for various aspects of streaming audio processing
     - `audio-recorder.ts` uses a class-based approach with OOP principles
     - Both handle microphone access, MediaRecorder configuration, and audio chunks processing

2. **Architectural Inconsistency:**
   - `lib` directory contains a mix of:
     - Utility functions (streamingAudio.ts)
     - Class-like functionality (voiceActivityDetection.ts)
     - Configuration (configTypes.ts, configService.ts)
     - Constants (constants.ts)
   - `services` directory contains:
     - OOP service classes with methods for specific functionality

3. **Service Integration Updates:**
   - `services/azure-openai.ts` has been removed as it wasn't being used
   - New `services/openai-service.ts` centralizes all OpenAI interactions

### Recommended Organization

The application would benefit from a more consistent architectural approach:

1. **Move all service-like functionality to `services/`:**
   - ✅ Create an `OpenAIService` that centralizes all OpenAI API interactions
   - Create an `AudioService` that combines functionality from both `streamingAudio.ts` and `audio-recorder.ts`
   - Move Voice Activity Detection functionality to a `VoiceDetectionService` in the services directory

2. **Keep `lib/` for pure utilities and configuration:**
   - Configuration (configTypes.ts, configService.ts)
   - Constants (constants.ts)
   - Helper functions and types shared across multiple services
   - Pure utility functions that don't involve browser APIs or external services

3. **Separate interfaces/types:**
   - Consider moving interfaces and types to a dedicated `types/` directory or `lib/types/`
   - This would make it easier to maintain type definitions and prevent circular dependencies

4. **Service registration system:**
   - Create a simple service registry for better dependency injection
   - This would make it easier to mock services for testing

5. **Standardize on either functional or OOP approach:**
   - Currently the codebase mixes functional programming (utility functions) with OOP (service classes)
   - Recommend standardizing on OOP for services since this provides better encapsulation
   - Keep utility functions for helpers that don't need state

## Service Integration

### HeyGen Integration
HeyGen Streaming Avatar is only used on the frontend for rendering and animating the avatar to speak with lip-syncing. No processing or logic from HeyGen is used for generating responses.

### Azure Services Integration
Azure services are responsible for:
1. Transcribing speech to text using Azure OpenAI Whisper model
2. Processing text through Azure OpenAI chat completion to generate responses

### OpenAI Service Integration
The OpenAI service centralizes:
1. Prompt formatting and engineering
2. API calls with consistent error handling
3. Response parsing and metrics tracking
4. RAG pipeline for knowledge-based responses

The complete flow:
1. User speaks into microphone
2. Audio is processed and sent to Azure Whisper for transcription
3. Transcribed text is sent to the OpenAI service
4. OpenAI service formats messages, handles RAG if enabled, and calls the API
5. Response is passed to HeyGen avatar for lip-synced animation

## Configuration System
The application uses a typed configuration system defined in app/lib/configTypes.ts:

1. AppConfig interface defines all configurable aspects including:
   - Avatar settings (ID, language, background)
   - Admin panel settings
   - UI elements (titles, buttons, backgrounds)
   - Content (conversation starters, loading messages)

2. Configuration implementation:
   - Configuration values are defined in the app-config.json file at the project root
   - The ConfigService (app/lib/configService.ts) loads and merges configuration with default values
   - The defaultConfig object in configTypes.ts serves as a fallback when file loading fails
   - The getConfig() function loads settings from app-config.json and applies defaults for missing values
   - The updateConfig() function allows saving changes to the configuration file

3. How to modify configuration:
   - Edit app-config.json directly for permanent configuration changes
   - Use the ConfigService.updateConfig() method to update configuration programmatically
   - Default values in configTypes.ts should only be modified when adding new configuration options

4. How configuration is used:
   - Components import and call getConfig() from ConfigService
   - UI elements like logos, backgrounds, and text are set based on config values
   - Admin panel password is specified in the config
   - Avatar settings (ID, language, etc.) come from the config

## Application Flow
1. The main application renders the InteractiveAvatar component on the home page.
2. The InteractiveAvatar component provides a user interface for interacting with a virtual avatar using voice or text input.
3. When a user speaks, the audio is processed through a pipeline that:
   - Captures audio from the microphone
   - Processes it using Web Workers (when available)
   - Sends it to Azure services for transcription (via /api/transcribe)
   - Gets a response from the OpenAI service
   - Animates the avatar to speak the response
4. For knowledge-based questions, the RAG pipeline can be enabled to enhance responses with retrieved information.
5. The application also provides separate test pages for testing voice functionality without the avatar UI.

## Performance Optimization Features
1. Web Worker audio processing: Audio processing is offloaded to Web Workers to free up the main thread.
2. LRU caching: Chat responses are cached to improve performance for repeated queries.
3. Optimized API parameters: Default parameters are provided to the OpenAI API for faster responses.
4. Connection reuse: HTTP connection keep-alive is used to reduce connection establishment overhead.
5. Detailed performance metrics: All operations are timed and metrics are returned with API responses.
6. Voice Activity Detection (VAD): Used to detect when a user is speaking to optimize recording.
7. Streaming mode: Audio is processed in chunks during recording to minimize latency.
8. Optimized parameter profiles: Different parameters are used for interim vs. final audio chunks.
9. In-memory caching: Session data and transcription results are cached in memory for faster retrieval.
10. Connection pooling: Active connections are tracked and reused to avoid reconnection overhead.
11. OpenAI service prewarming: Service connections are prewarmed to reduce latency.

### StreamingAvatar Integration and WebRTC Troubleshooting

The Pandora application integrates HeyGen's StreamingAvatar component which uses WebRTC for real-time avatar rendering:

1. **Token Authentication**:
   - The application uses two separate token systems:
     - HeyGen API tokens from `/api/get-access-token` (required for StreamingAvatar)
     - Azure Speech tokens from `/api/speech-token` (for speech-to-text)
   - Using the wrong token endpoint will result in 401 Unauthorized errors

2. **Common WebRTC Issues**:
   - "Unknown DataChannel error" - Often related to network configuration or firewall issues
   - "Stream disconnected" - Connection to HeyGen servers was lost
   - The application includes automatic reconnection logic with a 3-second delay

3. **Avatar Initialization Flow**:
   - Token fetching: `/api/get-access-token` (POST method)
   - API warm-up: Pre-connects to APIs to reduce latency
   - StreamingAvatar creation: Initializes with the token
   - createStartAvatar: Configures the avatar appearance and behavior
   - Event listener attachment: For monitoring avatar state

4. **Debugging Tips**:
   - Check browser console for detailed error messages
   - Verify the HEYGEN_API_KEY environment variable is correct
   - Ensure your network allows WebRTC traffic (UDP ports, no strict firewalls)
   - For persistent issues, try a different network or disable VPN
