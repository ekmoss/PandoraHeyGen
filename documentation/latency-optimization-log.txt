# Latency Optimization Log

## Chat API Performance Regression Investigation (Priority #1)

After implementing the initial streaming approach, we observed a significant performance regression in the Chat API:
- Original implementation: 679.80ms
- Streaming implementation: 1,679.10ms
- Difference: +999.30ms (147% increase)

### Root Causes Identified

1. **Connection Management Issues**:
   - The streaming implementation was making multiple API calls without proper connection reuse
   - Missing `Connection: keep-alive` header in some calls
   - No proper timeout handling, leading to potentially hanging requests

2. **Cache Management**:
   - No caching was implemented for common phrases
   - Each request was processed as new, even when identical
   - Missing `cache: no-store` directive in fetch calls

3. **Request Structure**:
   - Different request payload organization between implementations
   - Potential cold start issues with the API

### Optimizations Implemented

1. **Response Caching with LRU**:
   - Added LRU cache for API responses with 10-minute TTL
   - Implemented cache key normalization (lowercase, trim)
   - Added cache hit tracking in metrics

2. **Connection Optimization**:
   - Added proper `Connection: keep-alive` headers
   - Implemented timeout handling with AbortController
   - Standardized HTTP headers across implementations

3. **Request Processing**:
   - Optimized error handling with proper cleanup
   - Improved metrics collection
   - Added more comprehensive logging

4. **Performance Monitoring**:
   - Added cache hit ratio tracking
   - Improved client-side latency reporting

## Streaming Audio Implementation Improvements

In addition to fixing the Chat API regression, we made several improvements to the streaming audio implementation:

1. **Chunk Size Optimization**:
   - Reduced chunk duration from 500ms to 300ms for faster initial processing
   - Increased minimum processable chunk size from 1000 to 1500 bytes to avoid noise
   - Added adaptive processing based on chunk characteristics

2. **Voice Activity Detection (VAD)**:
   - Implemented basic voice activity detection
   - Added sensitivity configuration
   - Skip processing for chunks without speech

3. **Intelligent Processing**:
   - Improved text completion detection with more sophisticated rules
   - Added processing timeout configuration
   - Implemented chunk batching for small audio segments

4. **Session Management**:
   - Added timeout detection for stale sessions
   - Improved sequence tracking
   - Added debouncing to prevent excessive processing

### Voice Activity Detection Implementation
```typescript
export function detectVoiceActivity(
  audioBuffer: Blob,
  sensitivity: number = DEFAULT_STREAMING_CONFIG.vadSensitivity
): Promise<boolean> {
  return new Promise((resolve) => {
    // If VAD is disabled or this is a large chunk, assume it contains speech
    if (!DEFAULT_STREAMING_CONFIG.vadEnabled || audioBuffer.size > DEFAULT_STREAMING_CONFIG.minChunkSize * 2) {
      resolve(true);
      return;
    }
    
    // This is a simplified approach
    // A real implementation would analyze the audio data using WebAudio API
    // For now, we'll use size as a simple heuristic combined with our sensitivity parameter
    const sizeThreshold = DEFAULT_STREAMING_CONFIG.minChunkSize * (1 - sensitivity);
    resolve(audioBuffer.size >= sizeThreshold);
  });
}
```

## Short Utterance Optimization Plan (Priority #1)

Recent research indicates that for short utterances, a different optimization approach is needed compared to longer conversations. Based on industry research and benchmarks:

1. **Immediate Transcription Pipeline**:
   - Switch to a "detect end of speech" approach rather than waiting for fixed chunks
   - Implement WebAudio-based Voice Activity Detection (VAD) to detect speech end sooner
   - Use a lower threshold for speech completion detection (200-300ms of silence)

2. **Parallel Processing**:
   - Begin API preparation during audio capture (pre-warm connections)
   - Start transcription as soon as we have a reasonable chunk, without waiting for completion
   - Implement speculative processing - prepare API call before transcription is complete

3. **Format Conversion Elimination**:
   - Use browser's native WAV recording capabilities where supported
   - Eliminate format conversion steps by directly using compatible formats
   - Create a format compatibility matrix for different browser/API combinations

4. **Response Streaming**:
   - Implement streaming responses from Chat API
   - Show partial AI responses as they arrive (similar to ChatGPT interface)
   - Use incremental result rendering to improve perceived performance

## Implementation Details

### 1. Improved Voice Activity Detection

```typescript
// Implementation of REAL WebAudio-based VAD
export function createVAD(audioContext: AudioContext, stream: MediaStream, options = {
  threshold: -45,         // dB threshold for speech detection
  silenceTimeout: 300,    // ms of silence to consider speech ended
  frequencyRange: [85, 255]  // Hz range to analyze (human speech)
}) {
  let analyser = audioContext.createAnalyser();
  let microphone = audioContext.createMediaStreamSource(stream);
  microphone.connect(analyser);
  
  analyser.fftSize = 1024;
  let bufferLength = analyser.frequencyBinCount;
  let dataArray = new Uint8Array(bufferLength);
  
  let silenceStart = performance.now();
  let isSpeaking = false;
  let onSpeechStart: Function | null = null;
  let onSpeechEnd: Function | null = null;
  
  function checkAudioLevel() {
    analyser.getByteFrequencyData(dataArray);
    
    // Calculate volume in target frequency range
    let sum = 0;
    let count = 0;
    
    for (let i = 0; i < bufferLength; i++) {
      const frequency = i * audioContext.sampleRate / analyser.fftSize;
      if (frequency >= options.frequencyRange[0] && frequency <= options.frequencyRange[1]) {
        sum += dataArray[i];
        count++;
      }
    }
    
    const average = sum / count;
    const volume = average / 255;  // Normalize to 0-1
    const dB = 20 * Math.log10(volume);
    
    // Detect speech vs silence
    if (dB > options.threshold) {
      if (!isSpeaking) {
        isSpeaking = true;
        onSpeechStart?.();
      }
      silenceStart = performance.now();
    } else if (isSpeaking && (performance.now() - silenceStart > options.silenceTimeout)) {
      isSpeaking = false;
      onSpeechEnd?.();
    }
  }
  
  const intervalId = setInterval(checkAudioLevel, 50); // Check every 50ms
  
  return {
    setOnSpeechStart(callback: Function) {
      onSpeechStart = callback;
    },
    setOnSpeechEnd(callback: Function) {
      onSpeechEnd = callback;
    },
    stop() {
      clearInterval(intervalId);
      microphone.disconnect();
    }
  };
}
```

### 2. Parallel Processing Strategy

For short utterances, we'll implement a new parallelized pipeline:

1. Start audio recording with higher quality settings
2. Initialize VAD module to detect speech start/end
3. Pre-warm API connections during audio capture
4. Begin transcription as soon as speech ends (don't wait for fixed chunks)
5. Use a speculative approach for very short utterances:
   - If utterance is <2 seconds, send to transcription immediately
   - For common greetings, pre-cache responses
   - Use client-side models for simple intent recognition

### 3. Optimized Audio Format Strategy

Based on browser and API compatibility testing:

| Browser | Best Format | Fallback |
|---------|-------------|----------|
| Chrome  | audio/webm  | audio/wav |
| Safari  | audio/mp4   | audio/wav |
| Firefox | audio/ogg   | audio/wav |
| Edge    | audio/webm  | audio/wav |

For Azure API compatibility:
- WAV format requires no conversion but produces larger files
- MP3 is well supported but requires conversion in some browsers
- WebM works directly in Chrome/Edge but needs proper codec specification

### 4. Quick Response Caching

For common short utterances like greetings and simple questions:
- Implement an aggressive client-side response cache
- Use a probabilistic data structure (Bloom filter) to quickly identify common phrases
- Prefetch responses for likely follow-up questions based on initial utterance
- Create a "fast path" for single-turn interactions
